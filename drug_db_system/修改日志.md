## 2026-10-14 修复：模型配置的三个坑（请求协议 / 端点地址 / 模型名）

**触发**：用户要用智谱的 API，核对 pi 源码时连出三个问题。

**坑 1：请求协议不统一（最严重）**

pi-ai 的 provider 各走不同协议：

| provider | 协议 | 端点 |
|---|---|---|
| deepseek / zai* / moonshotai* / qwen* | `openai-completions` | `/chat/completions` |
| **openai** | `openai-responses` | `/responses` |
| anthropic | `anthropic-messages` | `/v1/messages` |

我原本把「智谱通用」和「自定义」都配成 `pi: openai`（借它的实现），
结果会把请求发到 `/responses` 上 —— **智谱和自建网关都不支持这个端点，必然 404**。

**坑 2：Base URL 会被拼错**

`validate()` 里原本的逻辑是"不以 `/v1` 结尾就补 `/v1`"，于是智谱的
`https://open.bigmodel.cn/api/paas/v4` 被拼成 `.../paas/v4/v1/models`（不存在）
→ **测连接永远失败，用户还会以为是自己 Key 填错了**。
这类"路径拼错伪装成密钥错误"最难排查。

**坑 3：模型名必须已注册**

`models.getModel(provider, id)` 实现是一次 `find`（`models.ts:483`），
**只在已注册的模型列表里查找**。用户填 `glm-4-flash` 这类不在内置清单里的名字，
直接取不到模型 → 报"模型不可用"。

**修复**

- `data/ai_providers.json`（v3）—— 新增 `api` 字段标明协议；智谱拆成两条：
  - `zai-coding-cn` → `https://open.bigmodel.cn/api/coding/paas/v4`（包月套餐）
  - `zai-general` → `https://open.bigmodel.cn/api/paas/v4`（按量计费）
  两者地址不通用，填错 404。`pi` 字段语义改为「模型定义模板来源」。
- `ai_model_config.py` —— 新增 `effective_base_url()` / `api_kind()` / `model_template()`；
  `validate()` 改为**多路径依次探测**（不再猜 /v1），401/403/429 立即返回
  （说明路径对、问题在密钥或额度），只有 404 才试下一个。
- `routers/ai.py` —— 透传给桥梁的改为「解析后的实际地址」+ 协议 + 模板
  （早先传的是用户原样值，用户没填时是空串，桥梁只能用它硬编码的地址，
  于是"选了通用 API 却打到 Coding 端点"）。
- **`ai-bridge/src/provider.ts`（新增）** —— 用 `createProvider` **自建 provider**：
  协议按请求指定、地址用用户的、模型列表只放用户填的那一个，
  模型定义字段从同协议的内置 provider 抄一份当模板（避免手写 `Model` 漏必填项）。
  这样三个坑一次解决，且**任意模型名都能用**。
  `LlmConfig` 下沉到 `config.ts`，消除 agent ↔ provider 的模块环。

**验证**

- 8 个供应商的 `api` 取值合法、`pi` 模板文件全部存在
- 假 Key 实测三家：智谱通用/Coding、DeepSeek 均返回 **HTTP 401**（
  `probe_url` 分别为 `.../paas/v4/models`、`.../coding/paas/v4/models`、`api.deepseek.com/models`）
  → **路径全部正确**，不再是 404
- ai-bridge 5 个 TS 文件语法检查通过，依赖方向单向无环

## 2026-10-14 修复：启动脚本把服务起错项目 + 后端端口与 ticketsys 冲突

**现象**：前端报「加载数据失败: Not Found」，后端日志 `[Errno 98] address already in use`。

**根因（两个，都在 `start.sh`，与 AI 代码无关）**

1. **`PROJECT_ROOT` 硬编码指向原项目**。`CRDB_AI/drug_db_system/start.sh:15` 写死
   `/mnt/d/Desktop/Project_Group/CRDB/drug_db_system`（复制项目时没改），
   于是在 CRDB_AI 目录里跑 `./start.sh`，启动的其实是 **CRDB 的代码** ——
   新加的接口全 404，看起来像代码坏掉。
2. **后端端口 8000 被 `ticketsys-api` 容器占用**。`free_port()` 靠 `ss -tlnp` 取 PID，
   而 docker 容器进程属 root、取不到 PID，于是静默跳过 → 后端绑定失败；
   前端却仍代理到 8000，**所有 `/api` 请求打到了 ticketsys 上**（正是那个 Not Found）。

**改动**

- `start.sh`
  - `PROJECT_ROOT` 改为 `$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)`，**复制到任何目录都不会再起错**
  - `BACKEND_PORT` 默认 `18000`（8000/8080/80/443/5432 均被占用），可环境变量覆盖
  - 新增 `export VITE_BACKEND_URL`，前端代理与后端端口**联动**，不会两处各写一个数字
  - `free_port()`：端口被占但拿不到 PID 时（=docker 容器）**直接报错退出**并给出排查命令，
    不再静默继续导致"打到别的服务上"
  - Excel 目录找不到 xlsx 时给出明确提示（仅影响导入，不影响查询）
  - 启动横幅增加「项目路径」「代理目标」，一眼能确认起的是哪个项目
- `frontend/vite.config.ts` —— proxy target 改读 `VITE_BACKEND_URL`，默认 `http://127.0.0.1:18000`
- `backend/main.py` —— `python main.py` 默认端口 18000 且可用 `BACKEND_PORT` 覆盖；补充端口说明

**验证**：在 18000 起后端，`/api/health` 返回 ok，13 个 AI 路由全部注册，未登录访问需鉴权接口返回 401。

## 2026-10-14 AI 问数：真实数据联调（补齐两个执行器 + 修复 6 处）

**背景**：首次连真实库联调。数据规模 dashenlin **861 万行**（2025-01-01~2026-09-30）、gaoji 96 万、haiwang 33 万。

**补齐执行器**：`q_turnover`（动销率）、`q_kpi`（经营大盘）—— 均通过显式传参直调 router 函数（`Query(...)` 默认值只在缺省时生效），不改原函数签名。

**真实数据暴露的 6 个问题（均已修）**

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | **数据可得性校准一直静默失效** | `get_data_range`/`hot_regions` 用 `str.format()` 拼 `sql.Identifier`，渲染成 `Identifier('日期')` 报错，被 `try/except` 吞掉后返回 `None` | 改用 `sql.SQL(...).format()` |
| 2 | 动销率分母为 0（实销 8201 ÷ 库存 0） | **销售表省份「广东省」、库存表「广东」**，两表命名不一致 | `_expand_region_terms()` 两种写法都传 |
| 3 | 「广东省各城市」只返回一行 | 省份筛选下 `split=city` 时地域轴被换成省份列 | 改用 `dimension=province`（省份拆表、行=省内城市） |
| 4 | 「只要盒数」命中「含门店数」的缓存 | `cache_key` 漏了 `metric` | 补进 key |
| 5 | 门店排行/趋势等**永远过不了校验** | `apply_defaults` 给能力未声明的槽位也补默认值，被判「不支持槽位」 | 默认值只补 `supports` 内的；校验时值等于默认值视为「没填」 |
| 6 | 门店数回答为空 | 门店数不产出 `total/footer`（去重计数不可加） | 取行内 `cells` 最大值作展示值 |

**性能实测**（dashenlin）

- 瓶颈是 `COUNT(DISTINCT)`：同条件 `SUM` **0.61s** vs `COUNT(DISTINCT)×2` **3.10s**
- 已从主 SQL 剥离门店数后：只要盒数+金额 **1.1s**；含门店数 **5.3s**；单城市 **0.65s**；缓存命中 ~0s；全国+同比最坏 **6.2s**

**发现但没擅自改（需你确认）**：库里**缺 `(省份,日期)` 复合索引**，且 `schema_def.py` 里声明的 `idx_dashenlin_date`、`idx_dashenlin_city_date`、`idx_dashenlin_city_prod_month_store` **在实际库中并不存在**（数据大概是直接导入、没跑 `create_indexes.py`）。当前省份查询走的是 `Parallel Seq Scan`。建议补 `(省份,日期)` 与 `(省份,月度,门店编码)`，预期能把 5~6s 降到 1~2s——但建索引要占磁盘且锁表，需要你决定。

**验证结果**：9 项能力 × 3 库 **全部通过**（0 失败）。

## 2026-10-14 AI 问数：确定性槽位提取 + 确认卡「问全」+ SQLite 埋点（首版）

**需求**：主页 AI 助手此前是纯前端 mock（回复硬编码）。改为真实问数：用户说人话 → 系统选口径 → 查数 → 给结论。**条件缺失时必须反问补齐，不许盲目执行**；要记录用户提问以便后期用数据优化。

**核心决策（为什么不做 Text-to-SQL / 多轮 ReAct）**
1. 系统的统计能力是**有限且封闭**的（盒数/金额/门店数/门店排行/趋势/动销率），要做的不是"理解数据库"，而是"把一句话翻译成一组已存在的参数"。故用**槽位填充**，不生成 SQL。
2. 不让 LLM 做分词/归一化：日期幻觉风险最高（"1-9月"可能被解析成 ~09-30 / ~今天 / ~09-31），且不可回归。改为**确定性提取器（纯规则，0 token，可单测）**，LLM 只在长尾兜底。
3. **多指标一次扫描**：`SUM(数量)`、`SUM(数量×开票价)`、`COUNT(DISTINCT 门店)` GROUP BY 键完全相同，可并列在同一条 SQL；再套三窗 `CASE WHEN`，本期/去年同期/上期一次扫完。即"问得越模糊给得越全，但扫描量不变"。
4. **反问做成「确认卡」而不是机器人轮流追问**：一次把 8 个槽位全列出来（已识别绿 / 待确认黄 / 必填红），用户点几下提交；`ready=false` 时"查询"按钮不可点，从机制上杜绝盲目执行。

**新增文件（后端）**
- `backend/data/ai_capabilities.json` —— 能力目录（Python 校验 + Node typebox schema 的**单一真源**）
- `backend/app/services/ai_capabilities.py` —— 加载/别名命中/plan 校验/补默认值

- `backend/app/services/ai_executor.py` —— 直接 import 既有统计函数执行（不走 HTTP），多指标一次扫描，模板化回答

- `drug_db_system/ai-bridge/`（与 `drug_db_system/pi/` 同级）—— Node 桥梁，接 pi-agent-core，**pi 源码零改动**

**修改文件**

## 2026-09-20 账号体系改造：用户自设密码 + 手机号登录 + 管理员删除让其重新申请

**需求**：申请账号时用户自己设置密码；管理员看不到密码，但可重置/删除让用户重新申请；登录用「手机号 + 密码」。

**改动**：
1. 申请表 `crdb_applications` 新增 `password_hash` 列（幂等 `ALTER` 兼容旧库），申请时存用户自设密码的 bcrypt 哈希，明文不落库。
2. `/api/auth/apply` 新增必填 `password`（走 `validate_password_strength`：≥8 位、含字母+数字）；同手机号已有待审申请、或已是成员则拒绝。
3. `/api/auth/applications/{id}/approve` 审批时**沿用申请人自设哈希**建账号（`create_user_with_hash`），**不再生成/回显任何明文密码**；缺少哈希的旧版申请直接拒绝并提示重新提交。
4. **移除**管理员「重置密码」接口（管理员无权设定密码），改为 `DELETE /api/auth/members/{uid}`：删除账号，让其用手机号重新申请并自设密码；禁止删管理员与删自己。
5. `/api/auth/login` 改为**手机号 + 密码**（新增 `get_user_auth_by_phone`）；按手机号查不到时按账号名兜底一次，保证未登记手机号的管理员账号仍可登录。

**涉及文件**：
- `backend/app/auth.py`、`backend/app/routers/auth.py`

## 2026-09-20 数据看板性能优化（第一批：图表实例持久化）

**改动**：看板各 echarts 容器改为**只在首次「有尺寸」时 `init` 一次**，之后一律 `setOption` 增量更新 / `resize`，去掉每次渲染时的 `dispose + 重新 init`，避免整屏图表反复重建（即用户所说的"整个界面重绘"）。

- 切指标/金额单位：仅前端 `setOption`（后端已同时返回盒数与金额，不重新请求）。
